### Security: The audited exports need the CSRF token from a browser session

`GET /api/v1/configuration-items/{id}/impact/export`,
`GET /api/v1/business-services/{id}/members/export` and `GET /api/v1/admin/config/export` are
recorded in the audit log, and the impact export also uses the caller's impact analysis capacity.
Until now they did not need a CSRF token, because they are reads, and the session cookie is sent
along when a user follows a link from another site. A page on another site could therefore start an
export as the signed-in user, which left an `export` audit entry in their name ([GH#414]). A request
with the session cookie must now send the `X-CSRF-Token` header on these three exports, as it does
on writes. Without the header the request answers 403 `CSRF_TOKEN_INVALID` and nothing is recorded.
The web UI already sends the header. API tokens (`Authorization: Bearer`) still need no CSRF token
on the two CSV exports; the configuration export stays limited to signed-in sessions.

**Upgrade:** a script that downloads these exports with a session cookie must send the
`csrfToken` from `POST /api/v1/auth/login` or `GET /api/v1/auth/me` as `X-CSRF-Token`, or switch
to an API token where the export accepts one.
