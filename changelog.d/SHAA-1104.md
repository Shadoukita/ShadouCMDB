### Security: the admin password and MFA resets refuse the caller's own account

Changing your own password or turning your own two-factor authentication off asks for your current
password (and a code, once MFA is set up), so a stolen session cannot turn into a known password.
The administration routes `PUT /api/v1/admin/users/{id}/password` and
`DELETE /api/v1/admin/users/{id}/mfa` asked for neither and accepted the caller's own id: a hijacked
session holding `users.manage` could set a password of its choice, drop the authenticator and end
the real user's other sessions, a permanent takeover of the account ([GH#413]).

Both routes now answer `409 CONFLICT` when `{id}` is the caller's own account, change nothing and
write no audit row. The message points to the self-service routes, `PUT /api/v1/auth/password` and
`DELETE /api/v1/auth/mfa/totp`. Resetting another user is unchanged.

**Upgrade:** nothing to do. Administrators who reset their own password or MFA from the user
administration page use their own account settings instead; a lost authenticator is reset by
another administrator. Scripts that called these routes with the caller's own id get `409` and must
use the self-service routes.
