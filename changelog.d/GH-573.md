### Changed: error responses list at most 100 field problems

An error response carried one `error.details[]` entry per problem, with no upper bound. A single
oversized request could make the server build and send a response many times larger than the
request itself: a workflow grants or draft `PUT` of 130 to 860 KB was answered with 3 to 9 MB of
details ([GH#573]).

Every error response, on every route and for every error code, now keeps the first 100 entries of
`error.details`. When there are more, it adds one last entry that counts the rest:

```json
{ "in": "body", "field": "", "code": "truncated", "message": "153 more problems not shown" }
```

That entry's `field` is empty, its `in` is that of the first problem left out, and its `message`
gives the number of problems not shown. A response with 100 problems or fewer is unchanged. Import
issue lists are paginated and not affected. The `ErrorEnvelope` schema in the OpenAPI document
describes the limit.

**Upgrade note:** API clients and scripts that map `details[].field` to form fields or input
columns should treat an entry with `code` `truncated` as a message for the whole request, not as a
problem with a field named `""`, and should not assume that `details` lists every problem. To see
the rest, fix the problems shown and send the request again. The bundled web UI already shows
entries with an empty `field` as a form-level error, so no action is needed there.
