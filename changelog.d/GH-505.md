### Security: an XLSX import can no longer hold hundreds of megabytes with a table of empty shared strings

The XLSX preflight capped `xl/sharedStrings.xml` at 64 MiB of XML, but the parser keeps one string
per entry and reserves the count the part declares up front. A small upload whose part was filled
with empty entries (`<si/>`, 5 bytes each) cost about 320 MB per analysis, paid again on each re-read
and once per import worker ([GH#505]). The preflight now also refuses a workbook with more than
2,097,152 shared-string entries, or whose `uniqueCount` claims more, with the error code
`too_many_shared_strings` and the message "The workbook holds more than 2,097,152 distinct text
values. Split the file and import it in parts." A `uniqueCount` that is not a plain number is
refused as `not_a_workbook`. The cap allows twenty distinct text values in
every row of a 100,000-row import (the default `IMPORT_MAX_ROWS`), and the table holds only distinct
values, so repeated text such as statuses or locations does not count again. Starting an import requires `cis.import`.

**Upgrade:** nothing to do. No API or schema change.
