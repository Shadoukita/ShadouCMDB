### Fixed: the systemd install accepts the documented number of connections

The shipped systemd unit set no open-files limit, so the server ran with systemd's soft limit of
1024 and accepted at most 768 open connections instead of 2,048 at the default
`HTTP_MAX_CONCURRENT_REQUESTS` ([GH#562]). The descriptors kept back from that limit also left out
the database pool, so a small `ulimit -n` with a large `DATABASE_POOL_MAX` could still run the
process out of descriptors.

- `deploy/systemd/shadoucmdb.service` now sets `LimitNOFILE=65536`.
- At start-up on Linux, the server raises its soft open-files limit to the hard limit.
- The descriptors kept back are a quarter of the limit, and never fewer than `DATABASE_POOL_MAX`
  plus 64.
- The `connection limit` line logged at start-up now shows the open-files limit (`open_files`) next
  to `max_connections`.

**Upgrade:** if you install the unit from the release archive, copy the new
`shadoucmdb.service` to `/etc/systemd/system/` and run `sudo systemctl daemon-reload` before you
restart. If you keep your own unit, add `LimitNOFILE=65536` to its `[Service]` section. No API or
schema change.

[GH#562]: https://github.com/Shadoukita/ShadouCMDB/issues/562
