### Security: one oversized audit row no longer stops the SIEM export over UDP

With `AUDIT_EXPORT=udp://…`, a row larger than one UDP datagram (about 64 KB) could never be sent, and
export retried it forever, so no later row reached the SIEM ([GH#179]). Anyone holding an API token,
even a revoked or expired one, could produce such a row: a `token.use` row stored the request path as
sent. The export now sends a row that does not fit as a stub (`oldValue` and `newValue` null,
`oversize` true, `originalBytes`) with its `chainSeq` and `rowHash`, and moves on; the full row stays in
the database. The server warns at startup when the export uses UDP, whose delivery is not
acknowledged.

`token.use` keeps the first 512 characters of the path, then `…`, with the full length in
`pathLength`. A token that can no longer authenticate (revoked, expired, owner disabled, profile
deleted) is recorded at most once a minute per outcome: a replayed dead token no longer adds an audit
row per request. The next row counts the requests left out in `unrecordedRefusals`. Accepted uses and
`session_only` / `forbidden` refusals are still one row per request.

**Upgrade:** nothing to do. No API or schema change. SIEM rules that count refused `token.use` rows
should add `unrecordedRefusals`. Prefer `tcp://` for the export where your collector supports it.
