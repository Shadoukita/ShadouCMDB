### Added: Workflow-driven state fields, bootstrap and auto-start

- **The state field follows its workflow.** While an active workflow drives a state field, the field
  can only change through the workflow (start, transitions, forced states). This applies whether or
  not the CI has an instance yet. A direct write is refused with the new error
  `409 WORKFLOW_CONTROLLED_FIELD`, with a detail on `attributes.<key>` and the code
  `workflow_controlled`. That covers `PATCH /api/v1/configuration-items/{id}`, `POST
  /api/v1/configuration-items` and bulk import and bulk edit, where each refused row is a row error.
  Writes that leave the value unchanged are accepted, so a form that saves every field still works.
  A new CI may leave the field empty or give it the workflow's initial value or the field's default.
  Deactivating the workflow makes the field editable again.
- **Bootstrap.** `POST /api/v1/admin/workflow-definitions/{id}/bootstrap` with
  `{"stateFromAttribute": true, "dryRun": …}` (needs **Manage workflows**) adopts a workflow on an
  existing inventory. Every live CI the workflow covers that has no running instance of it gets one,
  in the state mapped to the CI's current state field value. CIs whose value no state maps, and CIs
  in a terminal state, are reported and skipped. The dry run only counts. The run works in batches of
  1,000 CIs, each committed on its own. Run it again to finish a run that stopped part way: CIs that
  already run the workflow are left alone, so a second run starts nothing. Each start is recorded as
  `workflow.start` on the CI with actor type `system`, naming the administrator in `requestedBy`.
- **Auto-start.** A workflow with `autoStart` now starts on every new CI it covers. A CI created
  through the web UI or the API gets its instance, its initial state value and a `workflow.start`
  audit row in the same transaction. Bulk import starts the instances for the CIs it creates and
  writes **one** `workflow.start` audit row for the whole import (entity `import_jobs`, with the
  number of instances). The import's commit counts report it as `workflowsStarted`, and each instance
  still has its own start event.

**Upgrade note.** Activating a workflow with a state field makes that field read-only on every CI the
workflow covers. Before you activate it, check the `UNINSTANCED_CIS` warning. Run the bootstrap
dry run, map the values it reports as unmapped, then run the bootstrap.
