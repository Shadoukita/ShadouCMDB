### Security: A sign-in in progress no longer outlives a password reset or disable

A sign-in whose password (or second factor) was checked just before an administrator reset the
user's password, or disabled the account, could still complete once the reset or disable had
committed ([GH#209]). The session it opened survived the reset; after a disable it was unusable
but became valid again when the account was re-enabled. With MFA set up, the second-factor step
started with the old password survived the reset in the same way.

A session or second-factor step is now created only while the account is still active and still
has the password that was checked. Otherwise the sign-in is refused with `401 UNAUTHENTICATED`
("The account was changed during the sign-in"), no session or second-factor step is left behind,
and a `login.failure` audit row with `reason: "account_changed"` is written. The user signs in
again with the current password. This applies to local, directory (LDAP) and OIDC sign-ins;
`last_login_at` is now recorded only for a sign-in that actually opened a session.

**Upgrade:** nothing to do; no configuration or schema change.
