### Security: directory-account sign-ins during a directory outage are throttled and audited

While an LDAP/AD directory could not be reached, a sign-in with the name of a directory account got
`503 IDENTITY_PROVIDER_UNAVAILABLE` immediately. That answer was not throttled and not audited, so
for the length of the outage an anonymous client could test any number of names and find out which
ones are directory accounts, without leaving a record ([GH#586]).

That `503` now costs what a wrong password costs:

- It is answered no earlier than `SIGN_IN_FAILURE_FLOOR_MS` (default 1 s), like the `401`.
- It counts as a failed sign-in for the throttle: from the 5th in a row for a name from one client
  network, the name is locked with the usual backoff (`429 RATE_LIMITED`), and it counts towards
  the server-wide budget that slows sign-in when many names are tried.
- It is recorded as `login.failure` with `reason: "directory_unavailable"`, like unknown names
  during an outage.

**Behaviour change:** a directory user who keeps retrying while their directory is down can now be
locked for a short time on their own network (1 s, 2 s, 4 s, ...). A successful sign-in once the
directory is back clears the lock. The `503` itself still tells a directory account apart from other
names during an outage; that was accepted in GH#499.
