### Changed (breaking API change): Every user account is linked to a Person, and e-mail addresses are required and unique

Every sign-in account now has an e-mail address, unique regardless of case, and is linked to exactly
one CI of the new built-in **Person** type (area **People**). The Person type has the fields Name,
Email, Department, Phone and Job title. Administrators can add more fields. The type and its Name
and Email fields can't be deleted, archived, made optional or retyped.

- Creating a user, first-run setup, `shadoucmdb create-admin` and the first sign-in through an OIDC
  provider or LDAP directory all link the account to the Person with the same e-mail. If no such
  Person exists, one is created, named after the account's display name. A Person without an account
  is adopted, and a deleted one is restored.
- The account's e-mail is the source of truth. Changing it (`PATCH /api/v1/admin/users/{id}`)
  changes the Person's Email in the same transaction. The change is refused (409) when another
  account or another Person already has the address. On a linked Person the Email can't be edited
  (409 `managed_by_user`), and the Person can't be deleted or change its type (409 `person_linked`).
  Disable or delete the account first. Deleting an account leaves its Person in place.
- An identity provider that sends a new address another account or Person already has: the account
  keeps its old address, and a warning is logged. A new account whose address is taken is created
  without an e-mail: the user enters one after signing in, and the account's `create` audit row
  records the address in `providerEmailConflict`. So nobody who claims an address first can lock
  its owner out.
- An OpenID Connect `email` claim is used only when the ID token's `email_verified` is true.
- An account with an e-mail but no linked Person can't sign in. It gets the same answer as a wrong
  password, and the audit log records `account_incomplete`. Its sessions end. API tokens of such
  an account are refused too (401, `token.use` outcome `account_incomplete`), and so are tokens of
  an account that has no e-mail yet (403 `EMAIL_REQUIRED`, outcome `email_required`) until the
  user enters one.
- Every link, unlink and automatically created Person is audited: an `update` row on the account
  that shows its `person`, and a `create` (or `restore`) row on the Person.

API changes:

- `POST /api/v1/admin/users`, `POST /api/v1/setup` and `shadoucmdb create-admin` require `email`
  (`--email`). On `PATCH /api/v1/admin/users/{id}`, `email` can no longer be set to null.
- User objects gain `person` (`{id, label}`) and `signInStatus` (`ready`, `email_required` or
  `person_missing`). `GET /api/v1/admin/users` filters by `signInStatus` and `personCiId`.
- New `GET /api/v1/configuration-items/{id}/sign-in-account`: the account a Person is linked to.
- New `PUT /api/v1/auth/email` and error code `403 EMAIL_REQUIRED`, see the upgrade notes below.
  `GET /api/v1/auth/me` gains `emailRequired`.
- Attribute definitions gain the read-only `systemRole` (`person_name`, `person_email`).

**Upgrade:** take a backup, then run `shadoucmdb migrate`.

- If several accounts share an e-mail address (ignoring case), migration 0043 stops and lists them.
  Nothing is changed. Give each account its own address with the previous release, then run
  `migrate` again.
- `migrate` creates the Person type. It is keyed `person` in the area `people`, or `person_2` and
  `people_2` when those keys are taken. `migrate` then links every account that has an e-mail to a
  new Person and prints how many it linked.
- Accounts without an e-mail keep working: after their next sign-in they must enter one before
  anything else (every other route answers 403 `EMAIL_REQUIRED`). They are listed under
  Administration > Users with the sign-in status "e-mail required". Service accounts that sign in
  with API tokens only are not affected until someone signs in with them.
