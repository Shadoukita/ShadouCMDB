### Security: first-run setup needs a one-time setup token

Until the first administrator existed, anyone who could reach a new installation could create that
administrator through first-run setup ([GH#192], risk T14). Setup now needs a one-time **setup token**
that only the operator can read:

- When `serve` starts on a database without users, it generates the token and writes it to the log (a
  `WARN` line with a `setup_token` field) and to a file only the service account can read:
  `SETUP_TOKEN_FILE`, or `setup-token` next to the env file. The first-run page asks for it.
- `POST /api/v1/setup` takes it as `setupToken`. A missing one answers 400 `VALIDATION_ERROR`, a wrong
  one 403 `FORBIDDEN`. Once the first administrator exists the token stops working and the file is
  deleted; the answer is 409 as before.
- `SETUP_TOKEN` (at least 32 characters) sets the token instead, for unattended installs or several API
  processes. `SETUP_TOKEN_FILE` chooses where a generated one is written.
- The sample systemd unit gets `StateDirectory=shadoucmdb` and writes the token to
  `/var/lib/shadoucmdb/setup-token`.

**Upgrade:** installations that already have users are not affected. Scripts that complete first-run
setup through the API (not `create-admin`) must send `setupToken`: set `SETUP_TOKEN` for the server and
send the same value. If you use the sample systemd unit, copy the new version so a generated token can
be written.
