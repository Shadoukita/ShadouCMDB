### Security: anonymous requests count against the request cap

`HTTP_MAX_CONCURRENT_REQUESTS` was documented to exempt only `/healthz`, `/readyz` and
`/api/v1/version`, but every anonymous `GET` was exempt ([GH#219]): the setup status, the sign-in
options, OIDC sign-in and its callback, and the login page branding and logo. A flood of such
requests queued on the database connection pool, and on the OIDC routes opened unbounded
connections to the identity provider, instead of being answered `503 SERVER_BUSY`.

These routes now draw from the same pool as sign-in (one eighth of `HTTP_MAX_CONCURRENT_REQUESTS`,
at least 16), so an anonymous flood can delay the login page and sign-in but not signed-in users or
API tokens. The three health routes stay exempt, so monitoring does not report a busy server as down.

**Upgrade:** no configuration change. If monitoring or a load balancer probes the login page or
`/api/v1/auth/providers`, move the probe to `/healthz` or `/readyz`: under heavy load those other
routes may now answer `503` with `Retry-After: 1`.
