### Security: Shared saved views respect class restrictions in the audit log, counts and edits

Users whose profile limits the CI classes they may view are now held to those limits for shared
saved views everywhere, not only on the saved-view pages:

- **Audit log.** An entry about a shared view that names only classes the user may not view (one
  the saved-view API already answers with `404`) is left out of `GET /api/v1/audit-log` and of
  `page.total`. Before, its name, description, filters and columns were shown (GH#506).
- **Shared view count.** `limits.shared.used` in `GET /api/v1/saved-views` counts only the shared
  views available to the caller. The instance limit of 500 still counts every shared view. Shared
  view names stay unique per context across the whole instance, so a name already taken by a
  shared view you cannot see is still refused as a duplicate (GH#507).
- **Changing and deleting shared views.** Changing or deleting a shared view now needs
  `views.share` **and** the right to view every class the view names; otherwise the API answers
  `403` and `canEdit` is `false`. Before, a user who saw only part of a view could rewrite its
  filters or delete it for everyone. Copying the visible part is still allowed. A configuration
  import skips such a view with a warning, as it does for views the importer cannot see (GH#508).

**Upgrade:** no action. A curator who must maintain a shared view across classes needs view rights
on all of them, or an administrator makes the change.
