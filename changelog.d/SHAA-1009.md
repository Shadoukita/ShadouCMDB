### Security: Audit log ids no longer reveal hidden entries to restricted readers

A reader with `audit.view` whose profile limits the classes they may view no longer gets the stored
sequence number as `id` in `GET /api/v1/audit-log` ([GH#378]). The entries written by one request get
consecutive numbers, so a gap between two entries of a request they could see showed that an entry
they may not see was written in between. They now get a keyed permutation of the number instead. It
is still an integer, stable and distinct per entry, but it says nothing about order or about other
entries. It is derived from the encryption key (`ENCRYPTION_KEY_FILE`), so it changes when that key is
rotated. Readers who may view every class still get the stored sequence number. To order entries, use
`occurredAt` and the list order, never `id`.

**Upgrade:** nothing to do. An integration that reads the audit log with a class-restricted token and
stored `id` values sees new values for the same entries after the upgrade.
