### Security: guessing a password no longer locks the account holder out; sign-in timing no longer reveals local accounts

Five wrong passwords for a username locked it for everyone, and a correct password was refused while
it was locked, so one wrong guess per lock period could keep an account (the break-glass
administrator, say) locked indefinitely ([GH#187]). The lock is now kept per username and client
network (the IPv4 /24 or IPv6 /64 of the client address): guesses from one network lock the name for
that network only, and the account holder still signs in from theirs. Failures from several networks
that add up to 15 (at most 5 counted per network) still lock the name for every network, with the
same backoff. Once the server-wide failure budget is spent and sign-ins queue in the slow lane, one
network can hold at most 4 of the 64 places, so a single source can no longer fill it and refuse
everyone else's sign-in. Throttling a signed-in user's attempts at their current password is
unchanged.

With an LDAP/AD directory enabled, a name no local account has and that the directory did not match
was refused without the password hash check that a wrong local password costs, so response times
told local accounts from other names ([GH#190]). That answer now costs the same check.

**Upgrade:** no API or schema change. The client network is taken from the TCP peer, or from the
forwarding headers of a proxy listed in `TRUSTED_PROXIES` (see the [GH#215] entry), whatever
`AUDIT_CAPTURE_CLIENT_IP` says; it is kept in memory for throttling only and never stored or logged.
Behind a reverse proxy, set `TRUSTED_PROXIES` to its address, or every client counts as one network.
