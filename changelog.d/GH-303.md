### Security: A password sign-in racing an authenticator set-up no longer opens a password-only session

When a user confirmed a new authenticator app, the sessions opened with the password alone were
ended ([GH#292]). A password sign-in that checked for an authenticator just before the confirm
committed could still open such a session just after it ([GH#303]). Under a profile with
`requireMfa`, that session reached the enrolment routes, including the password change; without
`requireMfa`, it had full access.

Confirming an authenticator and opening a session now lock the user's row in the same order. A
sign-in that started first opens its session before the confirm goes ahead, and the confirm ends
that session. A password-only sign-in (local or directory) that has to wait for the confirm gets no
session. It is refused with `401 UNAUTHENTICATED` ("Two-factor authentication was set up for this
account during the sign-in"), and a `login.failure` audit row with `reason: "mfa_enrolled"` is
written. The user signs in again and enters the code from the authenticator app.

**Upgrade:** nothing to do; no configuration or schema change.
