### Security: `audit-verify` no longer accepts deleted audit rows as retention

`shadoucmdb audit-verify --allow-gaps` could pass a chain from which recent audit rows had been
deleted. Two weaknesses in how a gap was classed as `retention` are closed:

- A gap at the start of the chain was accepted whenever any later `prune-audit` run existed, even one
  that deleted nothing, and a run that removed old rows also covered recent rows deleted next to them.
  `prune-audit` now records the `chainSeq` ranges it deleted in its `audit.purge` entry
  (`newValue.deletedRanges`), and a gap is `retention` only when those ranges cover every missing row
  and add up to the rows the run counts as deleted. ([GH#683])
- The API's database role could insert its own `audit.purge` entry, dated in the future, which then
  excused every gap before it. Only the owner of `audit_log` may now insert `audit.purge` entries, which
  is what `prune_audit_log()` runs as; the API and maintenance roles get a permission error. An
  `audit.purge` entry dated in the future, or more than an hour after the entry that follows it in the
  chain, accounts for nothing. ([GH#684])

Both needed the schema owner's rights to delete the rows; the SIEM copy (`AUDIT_EXPORT`) remained the
authority throughout.

**Upgrade:** migration `0060` runs on start as usual. `prune-audit` runs before this release recorded
no ranges, so if the chain has gaps that `audit-verify` reported as `retention`, the migration writes
one `audit.purge` entry with `scope` `legacy` listing them in `deletedRanges`, and they keep verifying.
Compare those ranges with the SIEM copy if you have reason to doubt the history before the upgrade.
A gap that only a future-dated `audit.purge` entry accounted for is now reported as `deleted`;
investigate it against the SIEM copy. Any row deleted after the upgrade, old or new, is `deleted`
unless a later `prune-audit` run records it. On a single-role install, where the API connects as the
owner, the new insert restriction cannot tell the two apart; split the roles with
`sql/bootstrap/10_split_roles.sql`.
