### Added: Layout templates, a default template per class and per-CI layouts

Detail page and form layouts are now named **layout templates** in the UI settings
(`layoutTemplates`: key, name, optional description, layout). Each class uses one as its default
(`layouts[].templateKey`); every CI of the class shows it unless the CI has its own layout. A class
without a layout entry uses the built-in **Standard** template (no tabs: the detail page's usual
arrangement), which is always present and can be renamed but not removed. Template names are unique
ignoring case; keys are stable, so renaming a template changes only its name.

A CI can show another template or a layout of its own: `GET`, `PUT` and `DELETE
/api/v1/configuration-items/{id}/layout`. `GET` returns the layout to render and where it comes from
(`class_default`, `template` or `custom`) in one call; `DELETE` resets the CI to its class's default.
Changing a CI's layout needs `customization.manage` **and** the edit right on the CI's class; reading it
needs the view right, like the CI. Each change is audited (entity type `ci_layout_overrides`, the CI's
id) and shown only to audit readers who may view the CI's class. A deleted CI keeps its layout.

`GET /api/v1/ui-settings/layout-templates/usage` lists, per template, the classes that use it and the
number of live CIs that show it, and the default template of every class. `PUT
/api/v1/ui-settings/class-layouts/{key}` sets a class's default template. A template that a class or a
live CI still uses cannot be removed: `PUT /api/v1/ui-settings` answers 409 CONFLICT naming them.
Restoring an earlier settings version and importing a configuration file keep such templates instead.

The settings the API returns still carry each class's layout on the class (`layouts[].tabs`,
`hiddenFields`, `readOnlyFields`, now taken from its default template), so the current layout editor
works as before: a layout saved for a class changes that class's default template, and every class
using the same template changes with it. A class layout sent without `templateKey` becomes a new
template "<class name> layout" that the class then uses.

Configuration files are now format version 7 (with `layoutTemplates`). Files of versions 1 to 6 still
import: their class layouts become templates, as on upgrade. Per-CI layouts are CI data and are not
part of configuration export and import. Older releases refuse version 7 files.

**Upgrade:** migration 0042 adds the `ci_layout_overrides` table and moves every stored class layout
into a template named "<class name> layout" that the class uses as its default, so every detail page
and form looks as before. It saves the converted settings as a new version (the previous one stays
in the history and can still be restored) and records the change in the audit log as
`migration 0042`. Nothing to do; take a backup first, as for any upgrade.
