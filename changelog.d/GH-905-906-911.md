### Security: tighter webhook endpoint administration (GH#905, GH#906, GH#911)

Hardening from security delta review #26:

- **Re-authentication to move an endpoint ([GH#906]).** `PATCH /api/v1/admin/webhook-endpoints/{id}`
  with `url` or `authHeader` now needs a session that signed in or confirmed its password
  (`POST /api/v1/auth/reauthenticate`) in the last 10 minutes, as creating an endpoint already did. API
  tokens and older sessions get 403 `REAUTHENTICATION_REQUIRED`, audited as
  `session.reauthentication_required`. Changing the name, timeout or rate limits works as before. The
  web UI opens its password confirmation dialog. Save again after confirming.
- **No webhook URLs in the audit log ([GH#905]).** The audit entries of a webhook endpoint (create,
  update, delete, suspend, resume, import) no longer hold `url`. They hold `urlOrigin`
  (`https://host[:port]`) and `urlSha256` (the hex SHA-256 of the full URL), because the path or query of
  an incoming-webhook URL is often its credential and `audit.view` does not imply `webhooks.manage`. To
  check whether an entry refers to a given URL, compare its SHA-256. Audit entries written before this
  release are not changed and may still contain full URLs. Restrict who holds `audit.view` and who
  receives audit exports accordingly.
- **Configuration import respects `WEBHOOKS_ALLOWED` ([GH#911]).** While webhooks are switched off,
  `POST /api/v1/admin/config/import` leaves the `webhookAllowedHosts` and `webhookEndpoints` sections
  unchanged and returns a warning for each one. The rest of the file is imported. Before this release, an
  import could stage endpoints that became active as soon as the operator set `WEBHOOKS_ALLOWED=true`.
