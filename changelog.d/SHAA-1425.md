### Added: Workflows in the configuration file (format version 8)

Configuration export and import now carry workflows, in a new optional `workflows` section. The file
format is now version 8; files of versions 1 to 7 are still read.

- **What is exported.** Each workflow's current published version, by key: its settings (type, state
  field, auto start, active), its graph (states, transitions, transition fields and conditions, the
  designer layout) and its grants by permission profile name. Drafts, retired versions, running
  instances and their history are never exported. Workflows that were never published are left out.
  The section needs **Manage workflows** (`workflows.manage`), on export (it is left out otherwise) and
  on import (403 otherwise).
- **Matching.** Workflows match by key, built-in types by their system role, fields by key on the
  workflow's type, lookup values by key, and profiles by name.
- **Import never changes a published version.** The file's graph is checksummed as a draft would be.
  An equal checksum changes nothing; a different one publishes a new version with the change note
  `Imported from configuration file` (running instances stay on their version); a new key creates the
  workflow and publishes version 1. Settings and grants are replaced. A workflow that has an
  unpublished draft here and a changed graph in the file is refused (409): publish or delete the draft
  first. A workflow never moves to another type.
- **Checked like a manual change.** Workflows import after the data model, lookups and profiles, in
  the same transaction. The publish lint runs on import: a graph with errors fails the whole import,
  with the problems reported at their path in the file (`workflows.0.graph.states[3]`). Every change is
  audited as if made in the API; an unchanged file writes no audit entry.

**Upgrade:** no migration. Files exported by this release (version 8) cannot be imported into an older
release.
