### Security: A requester can no longer choose the approver of a step whose approvers come from a CI field (GH#664)

An approval step can take its approvers from a reference field of the CI (approver source
`ci_attribute`, for example the server's **Owner**). A user with the edit right could set that
field to a colleague just before requesting, or while the request was pending, and so choose who
approved their own change. Four-eyes still kept the requester out, but separation of duties was
lost.

- **Approvers are fixed when the request is made.** Every step's approvers are now worked out
  when the request is created, not when the previous step completes. Editing the field while a
  request is pending no longer changes who decides a later step. An administrator's **Refresh**
  (`POST /api/v1/workflow-approval-requests/{id}/refresh`) still re-reads the CI, with the rule
  below.
- **Who set the field decides.** A field source is not used when the field's current value was
  set by the requester, or by the creator of the API token the request was made with. Edits in the
  web UI, through an API token and through a bulk import all count, however long ago they were
  made and whatever state the CI moved through since. Saves that left the value unchanged are
  ignored, so someone else re-saving the CI does not hide the requester's edit. A value set through
  an API token or import that recorded no user is not trusted either. A field with no audit history
  keeps its approvers.
- When a source is not used, the step falls back on its other approver sources. If none remain,
  nobody can decide the step: it shows as understaffed, and a workflow manager can cancel the
  request.
- `GET /api/v1/workflow-approval-requests/{id}` shows, per step, `droppedSources` (the source, the
  reason `field_set_by_requester` or `field_set_by_unattributed`, a message, and
  `fieldLastChanged`: who set the field and when). Each approver taken from a field shows
  `fieldLastChanged` too. The approver preview
  (`GET /api/v1/admin/workflow-definitions/{id}/approvers/preview`) shows `fieldLastChanged` per field
  source on the CI, and with `requestedBy` marks the sources that request would drop (`dropped`).
- The request's audit row (`workflow.approval_request`) records each step's eligible count and
  dropped sources; the refresh audit row records the dropped sources before and after.
- Upgrade: migration `0062` adds `dropped_sources` to approval request steps. Requests already
  pending keep their behaviour: their later steps are worked out when they become active.

Remaining limits: someone other than the requester can still set the field on their behalf (the
audit log shows who did); edits older than the audit retention period are not seen; and linking a
user account to a Person record is reserved to administrators.
