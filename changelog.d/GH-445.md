### Security: no DN-based directory identities, session-only configuration export, https CORS origins

Hardening from the security review ([GH#445]); none of these was exploitable without a privileged role or
a specific configuration:

- **LDAP/AD:** an account's stable identity is now always the entry's `objectGUID` (Active Directory) or
  `entryUUID` (OpenLDAP, 389 Directory Server). A directory entry that returns neither is refused at
  sign-in, before its password is sent, and `POST /api/v1/admin/identity-providers/{id}/test` reports
  "the directory returned neither objectGUID nor entryUUID". Previously the entry's DN was used instead, so a
  new entry that reused a departed user's DN took over that user's ShadouCMDB account and API tokens.
- **Configuration export:** `GET /api/v1/admin/config/export` now needs a signed-in session, like the
  import. An API token answers 403 `FORBIDDEN`, and the refusal is audited as a `token.use` entry with
  outcome `session_only`.
- **CORS:** `CORS_ORIGINS` refuses plain `http://` origins at startup unless they are loopback
  (`http://localhost:5173`, `http://127.0.0.1:8080`, `http://[::1]:3000`). The new
  `CORS_ALLOW_HTTP_ORIGINS=true` accepts them anyway, for closed test networks.
- **Documentation:** `.env.example` recommends `OIDC_ALLOWED_HOSTS` for hardened deployments. The README,
  `docker-compose.yml` and the Linux and Windows installation guides now say that the server speaks
  plain HTTP, that production needs a TLS reverse proxy in front, and how to bind the API to loopback
  when that proxy runs on the same host.

**Upgrade:**

- If the server no longer starts with `CORS_ORIGINS: "http://…" is a plain-HTTP origin`, serve that web
  UI over https and list its `https://` origin, or set `CORS_ALLOW_HTTP_ORIGINS=true`.
- Automation that downloads the configuration with an API token must do so from a signed-in session.
- Before upgrading, run the identity provider test for an LDAP user. If the service account cannot read
  `objectGUID` or `entryUUID`, grant it read access first. Otherwise directory sign-in stops working.
  Accounts first linked while neither attribute was readable were linked by DN, and cannot sign in
  through the directory any more. Once the attribute is readable, delete or rename such an account. The
  user's next sign-in then creates a new account linked to the stable id.

No schema change.
