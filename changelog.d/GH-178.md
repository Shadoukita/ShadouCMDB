### Security: an API token minted for another user cannot exceed its creator's rights

A user manager who is not an administrator could mint a token for another user with any permission
profile, including Administrator ([GH#178]). The token was capped only by its owner's permissions,
so when the owner was later promoted (directly or through an SSO group mapping), the token gained
rights its creator never held.

- **Creating** a token for another user (`POST /api/v1/api-tokens` with `userId`) now also requires
  that you hold every permission of the chosen profile yourself; otherwise the request is refused
  with `403 FORBIDDEN`. Tokens for yourself are unchanged: they are capped at your own rights.
- **Using** a token that someone created for another owner now grants only what the owner, the
  token's profile **and the creator's current permissions** all allow. If the creator loses a
  permission, their tokens for other owners lose it too; if the creator's account is disabled,
  those tokens have no permissions. Tokens created with the `shadoucmdb` CLI, and tokens whose
  creator is unknown, are capped by owner and profile as before.

No API schema or database change.

**Upgrade:** tokens minted for other users before the upgrade are capped at their creator's rights
from now on. A service token created by an administrator who has since been demoted may therefore
lose rights; mint a replacement from an account that holds them. This also closes the gap noted for
[GH#183]: tokens created by an account that was disabled before that fix no longer grant anything.
