### Added: Workflow definitions API (design time)

Administrators holding **Manage workflows** (`workflows.manage`) can now design workflows through
the API under `/api/v1/admin/workflow-definitions`. Running workflows on CIs comes in a later
release; until then a published workflow changes nothing for your CIs.

- **Definitions.** A workflow has a key (its export identity) and a CI type, both fixed, plus a name,
  a description and its flags. A new workflow is inactive. It can name a lookup field of its type as
  its *state field*, which it will keep in step with its state; only one active workflow may drive a
  field. A workflow that never ran on a CI can be deleted; one that ran is deactivated instead
  (409 `IN_USE`). Changes need the `version` the administrator loaded (409 `VERSION_CONFLICT`).
- **Activation warning.** Activating a workflow that has a state field returns
  `warnings: [{"code": "UNINSTANCED_CIS", "count": n}]`: the number of live CIs it covers that have no
  running instance yet. Their state field cannot be edited while the workflow is active, until an
  instance is started on them.
- **Drafts and versions.** The graph (states, transitions, the fields a transition asks for, and its
  conditions) is edited as one draft, replaced as a whole with `PUT …/draft`. `POST …/draft/validate`
  lints it: every state reachable, a way out of every non-terminal state, a terminal state reachable
  from each, and fields and values that exist and are active. `POST …/draft/publish` publishes it as
  an immutable version, refused with 400 and one detail per problem while the lint finds errors, and
  with 409 when the draft changed since it was validated (`expectedDraftChecksum`). Published versions
  can be retired; new instances then start on the newest version still published.
- **Conditions** are a small JSON language (`all`, `any`, and comparisons such as `eq`, `in`, `isSet`,
  `lte` or `contains` on fields of the type), checked against each field's data type. There is no
  scripting and no regular expression.
- **Grants.** `PUT …/grants` sets which permission profiles may run each transition (`_cancel`: who
  may cancel an instance).
- **Data model protection.** A field that a published workflow version uses (as a transition field,
  in a condition or as state field) can no longer be archived, given another type, list or enum values,
  or purged: 409 `IN_USE` names the workflows and versions. Purging also considers drafts. A lookup
  value a workflow state maps to cannot be deleted, and a type with workflows cannot be purged.
- **Audit log.** Creating, changing and deleting a workflow, grant changes and retiring a version are
  recorded as `workflow_definitions` entries; publishing as `workflow.publish` with the whole graph.
  Drafts are not audited.

**Upgrade:** no migration; this release uses the tables of 0046.
