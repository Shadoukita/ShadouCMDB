### Security: The audit export sends a backup.restore entry even when later rows follow it

`AUDIT_EXPORT` sent the `backup.restore` entry that `shadoucmdb restore` records only while it was
the last row of the audit log when the server started. Any command that wrote an audit row between
`restore` and the first `serve`, such as `mfa reset-undecryptable` (which `restore` recommends after a
key change) or `create-admin`, made the export skip it. The SIEM copy, the reference for spotting a
rolled-back audit chain, then never learned of the restore. ([GH#677])

The export now records each `backup.restore` entry it has sent. At start-up it begins just before the
oldest entry it has not sent, so that entry and every row written after it are sent, including the
rows CLI commands wrote before the server started. The server logs a warning when it starts this way.
Once an entry is sent, a restart resumes at the newest row, as before. If `restore` ran while
`AUDIT_EXPORT` was off, the entry and every row after it are sent when you turn the export on.

**Upgrade:** migration `0061` adds the table `audit_export_restores` (included in backups; the API
role may read and add rows but not change them) and an index on the `backup.restore` entries. To
apply it, run `shadoucmdb migrate` before starting the new release (`serve` does not migrate). An
existing `backup.restore` entry counts as sent only when the first audit row after it (other than
another `backup.restore` entry) came from a user or API client, meaning the server started with the
entry at the end of the log. An entry followed first by a row a CLI command wrote was never sent,
even if users signed in later, so it is sent at the next start, together with every row after it.
