### Security: OIDC client secrets and LDAP bind passwords are encrypted at rest

OIDC client secrets and LDAP bind passwords are now stored encrypted with the encryption key
(`ENCRYPTION_KEY_FILE`), like authenticator secrets. Existing values are encrypted on the first start.
Backups taken before this version still hold them unencrypted: if such backups have left your
custody, rotate these credentials at the identity provider ([GH#199]).

Each secret is bound to its provider and field, so a value copied elsewhere does not decrypt. A
stored secret that does not decrypt stops sign-in through that provider (`IDENTITY_PROVIDER_UNAVAILABLE`,
or `ssoError=unavailable` for OIDC) until an administrator enters it again; the connection test says
so. Backup headers and `shadoucmdb verify` now count these secrets per key, and `restore` warns
when their key is not configured. The new command `shadoucmdb identity-providers
reset-undecryptable [--dry-run] [--yes]` gives up the secrets under a lost key. It disables those
providers and clears their secret and a directory's bind DN, audited as an `update` with `reason:
key_lost`.

**Upgrade:** nothing beyond the encryption key setup this release already requires. Stop every
instance of the previous release first: once this release has encrypted the secrets, the previous
release cannot use them (its OIDC and LDAP sign-in fails and it cannot save provider changes), so
do not run both versions side by side during the upgrade. Migration 0026
adds `client_secret_enc`, `bind_password_enc` and `secrets_key_id` to `identity_providers`. The old
text columns stay NULL after the first start and are dropped in a later release. As for
authenticator secrets, `serve` refuses to start when provider secrets are under a key that is not
configured. Consider registering ShadouCMDB at the OIDC provider as a client with no application
permissions of its own (see `docs/security/hardening.md`, "Secrets at rest").
