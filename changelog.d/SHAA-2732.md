### Added: workflow transitions can set CI fields (attribute actions)

A workflow transition can now set fields of its CI when it runs, for example `retire` sets
`lifecycle_status` to `retired`, `retired_on` to today and `retired_by` to whoever retired it. The
actions are part of the workflow version (`setAttributes` on a transition in
`PUT /api/v1/admin/workflow-definitions/{id}/draft`): they take effect when the version is published,
they are part of its checksum, and the `workflow.publish` audit row records them. Each action sets one
field to a literal `value` (enum and lookup values by key) or to `valueFrom`: `now`, `today`, `actor`
(the Person linked to the user who runs the transition) or `clear`.

- **When they run:** in the transition's own transaction, after the fields the user entered and
  before the instance moves on. This applies to direct runs, bulk runs, and the final approval of a
  transition that needs approval, where the deciding approver is the actor. Conditions are checked
  before the actions, never on what they set.
- **Rights:** the actions add none. They write with the rights of whoever runs the transition (or
  decides its approval), limited to the edit right on the CI's type, with the same validation as a CI
  update.
- **Publishing refuses** an action on a workflow's state field, an identifying field, a field the
  same transition asks the user for, a key field of the Person type, a reference to another type than
  Person, or an archived field, as well as a value the field would not accept.
- **Failure:** if a value no longer validates when the transition runs (for example a lookup value
  deleted since publishing), the transition fails with the new 422 `WORKFLOW_ACTION_INVALID` and
  nothing is written. In a bulk run, only that item fails.
- **Audit:** the fields an action changed get their own CI `update` row with
  `source: {kind: "workflow_action", definitionKey, versionNo, transitionKey}` and the instance id
  (plus `approvalRequestId` and `requestedBy` on a final approval), so the history tells "set by the
  workflow" from "entered by the user". The instance's event history marks those fields
  `"origin": "action"`.
- A field that an action of a published version sets cannot be deleted or retyped (409 `IN_USE`
  names the workflow).
- The configuration file is now **format 14**: it carries `setAttributes` in the workflow graph.
  Files of formats 1 to 13 still import, with no actions.

**Upgrade:** nothing to do. Published versions keep their checksums.
