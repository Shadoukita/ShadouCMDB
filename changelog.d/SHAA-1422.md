### Added: Groundwork for workflows: the Manage workflows right, process types and workflow tables

This release prepares the database for workflows (states, transitions and their history on CIs).
Nothing changes for an install until an administrator publishes a workflow, which a later release
makes possible.

- **New global right: Manage workflows** (`workflows.manage`). It covers designing, publishing and
  retiring workflows, deciding who may run their transitions, and moving running instances. On
  upgrade it is granted to every permission profile that holds **Manage the data model**; review your
  profiles if workflow design should be a separate role.
- **Process types.** A CI type now has a kind: `asset` (every existing type) or `process`, for records
  such as change requests that live in a type table like assets but are not inventory. Records of a
  process type are left out of the inventory list, global search, the relationship graph, impact
  analysis, business service membership and the dashboard counts. `GET /configuration-items` and
  `GET /search` list them with `kind=process` (or `kind=any`), or when their type is named in
  `classId`. A type's kind is set when it is created (a subtype takes its parent's) and can change
  only while the type has never held a CI and has no subtypes. `GET /ci-classes` filters by `kind`.
- **Audit log.** New actions `workflow.publish`, `workflow.start`, `workflow.cancel`,
  `workflow.transition`, `workflow.migrate` and `workflow.force`, and the entity type
  `workflow_definitions`. They are pruned with the `changes` scope of `shadoucmdb prune-audit`.
  Workflow history itself (the instance events) is kept for the life of the CI and is never pruned.
- **Backups** include the new tables, and a factory reset empties them.

**Upgrade:** migrations 0046 and 0047 are additive and rewrite no data. The audit log's constraints
are checked in 0047, in a transaction of its own that does not block audit writes, so the upgrade
stays quick on a large audit log. On a three-role install the application role can read and add
workflow events but not change or delete them, as for the audit log.
