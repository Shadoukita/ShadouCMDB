### Security: Database role passwords stay out of the process list and the server log

The bootstrap scripts `sql/bootstrap/00_create_role_and_database.sql` and
`sql/bootstrap/10_split_roles.sql` took the role passwords as psql variables (`-v owner_password=...`).
The passwords were then visible to other users of the admin machine in the process list, and reached
the PostgreSQL server in plain text inside `CREATE ROLE ... PASSWORD`, where `log_statement = ddl` or
`all` and error reports wrote them to the server log ([GH#444]). The scripts now create the roles
without a password. Set each password afterwards with psql's `\password`, which prompts for it and
sends the server only a SCRAM-SHA-256 verifier:

```sh
psql "<admin connection string>" -c '\password shadoucmdb_owner' -c '\password shadoucmdb_app' \
     -c '\password shadoucmdb_maintenance'
```

The roles cannot log in until their password is set. For unattended setup, `\password` reads the
password and its confirmation as two lines from standard input when psql has no terminal; the
release README for Linux shows the command.

**Action on upgrade:** nothing for an existing installation. If you automate new installations or the
role split, drop the `owner_password`, `app_password` and `maintenance_password` variables from the
`psql` call and add the `\password` step: the scripts now stop with an error when one of those
variables is set. If an earlier setup ran with `log_statement = ddl` or `all`, the role passwords may
be in old server logs: change them with `\password`.
