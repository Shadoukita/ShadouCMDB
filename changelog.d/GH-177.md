### Security: concurrent inventory lists no longer exhaust the database connection pool

The inventory list, global search and relationship graph held one pooled database connection and then
took up to two more for the same request. About `DATABASE_POOL_MAX` concurrent list or search
requests (10 by default) could take every connection and wait on each other, so every request on the
instance stalled until the pool timed out, sign-in included ([GH#177]). Any signed-in user could
trigger this by accident or on purpose. Every request now uses at most one pooled connection at a time:
a page and its total are read one after the other on the same connection, the graph reads every hop on
the connection it already holds, and every other paginated list (users, profiles, API tokens, audit
log, relationships, classes, attributes, relationship types, lookups, areas) does the same. Turning
off two-factor authentication or replacing recovery codes with a wrong code no longer opens a second
transaction while the first one is still open.

**Upgrade:** nothing to do. No API or schema change. If you raised `DATABASE_POOL_MAX` only to work
around stalls under load, you can return it to the value that suits your database.
