### Fixed: `shadoucmdb backup` works on installations with separate database roles

On an installation with separate owner, API and maintenance roles (`sql/bootstrap/`), `shadoucmdb
backup` stopped with `permission denied for table audit_log_chain_head` and wrote no file ([GH#396]).
Migration 0038 lets the API role read the audit log's hash-chain head, so the backup runs as the API
role (`DATABASE_URL`), as documented. The API role still cannot change, delete or lock the head: only
the audit log trigger moves it, so the tamper evidence of the audit log is unchanged. `shadoucmdb
restore` still connects as the schema owner (`MIGRATION_DATABASE_URL`), and `shadoucmdb audit-verify`
passes on the restored database. Single-role installations were not affected.

**Upgrade:** run `shadoucmdb migrate` with `MIGRATION_DATABASE_URL` set, as for every upgrade; no
manual SQL is needed. `sql/bootstrap/10_split_roles.sql` grants the same read access when you split
the roles later. If you worked around the error by running `backup` with the owner role's
credentials, switch the backup job back to the API role and keep the owner's password out of it.
