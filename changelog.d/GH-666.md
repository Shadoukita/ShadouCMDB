### Security: starting a workflow again on a CI needs the `_start` grant

Any user with the edit right on a CI's type could start a workflow again on a CI where an instance
of it had completed or been cancelled. The new instance set the workflow's state field back to the
initial state, the change a direct edit refuses with `409 WORKFLOW_CONTROLLED_FIELD`. This undid a
lifecycle whose transitions that user was not granted, including ones that had passed approval. A
holder of the `_cancel` grant could do the same to a running instance by cancelling it and then
starting it again ([GH#666]).

- `POST /api/v1/workflow-instances` now also needs `workflows.manage` or the workflow's new
  **`_start`** grant when an instance of that workflow already ended on the CI. Otherwise it
  returns `403 FORBIDDEN`. The first start on a CI, and `autoStart` on new CIs, still need only
  the edit right.
- `GET /api/v1/configuration-items/{id}/workflows` lists such a workflow in `startable` only for
  callers who may start it again.
- The grants matrix in **Administration → Workflows** has a new row, 'Start again after an
  instance ended'. `PUT …/grants` and the configuration import accept `_start` as a transition
  key.

**Upgrade:** migration 0059 lets the grants table store `_start`. After the upgrade, only holders
of `workflows.manage` (including administrators) can restart a workflow on a CI where it ended.
If other teams restart lifecycles as part of their process, grant `_start` to their profiles.
