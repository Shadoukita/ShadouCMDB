### Security: user-management changes need a recently confirmed password

Since [GH#413] the administration routes refuse to reset the caller's own password or MFA. A
hijacked session that holds `users.manage` could still get around that without knowing any
password: create a second user manager (or reset the password of an existing one), sign in as it,
and reset the first account ([GH#498]). Creating an Administrator account or an API token in the
same way also gave it lasting access.

The changes that hand out or take over an account's rights now need a session whose owner
confirmed their credentials in the last **10 minutes**. Signing in counts. So does the new
`POST /api/v1/auth/reauthenticate`, which takes the current password and, once two-factor
authentication is set up, a current code (authenticator or recovery code). A wrong password or
code counts against the same per-user lock as on the other password confirmations. The routes
concerned:

- `POST /api/v1/admin/users`, `PATCH /api/v1/admin/users/{id}`,
  `PUT /api/v1/admin/users/{id}/password`, `DELETE /api/v1/admin/users/{id}/mfa`
- `POST /api/v1/admin/profiles`, `PATCH /api/v1/admin/profiles/{id}`,
  `POST /api/v1/admin/profiles/{id}/clone`
- `POST /api/v1/admin/api-tokens`
- `POST /api/v1/admin/identity-providers`, `PATCH /api/v1/admin/identity-providers/{id}`
- `POST /api/v1/admin/config/import`

Without a recent confirmation they answer `403 REAUTHENTICATION_REQUIRED` and change nothing.
Disabling an account is a `PATCH` and needs it too. Reads, deleting users and profiles, revoking
API tokens and testing an identity provider are unchanged.

Two new audit events, both kept for the `auth` retention period: `session.reauthenticate` (the
session's owner confirmed their credentials) and `session.reauthentication_required` (a change was
refused; `new_value` names the operation, method and path). A run of the second event against an
account its owner is not using points to a stolen session.

**Upgrade:** migration 0042 adds `sessions.credentials_confirmed_at`. Sessions open at the upgrade
count from their sign-in time, so after the upgrade administrators confirm their password (or sign
in again) before their next user-management change. Scripts that call these routes with a session
call `POST /api/v1/auth/reauthenticate` first (API tokens cannot call them anyway). Accounts of an
OIDC provider have no password here: they sign in again to open the 10 minutes.
