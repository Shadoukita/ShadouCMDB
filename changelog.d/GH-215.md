### Security: forged `X-Forwarded-For` headers no longer choose the sign-in throttle's network; new `TRUSTED_PROXIES`

The sign-in throttle keeps failures per username and client network, and took the client address
from the first `X-Forwarded-For` hop, whoever sent it ([GH#215]). With no reverse proxy, or one that
appends to the header (nginx `$proxy_add_x_forwarded_for`, most load balancers and ingress
controllers), a client could claim the account holder's office network, lock them out with five
wrong passwords, or rotate through made-up networks. The throttle now uses the TCP peer address,
unless the peer is listed in the new setting `TRUSTED_PROXIES`: then it reads `X-Forwarded-For` (or,
only when no `X-Forwarded-For` header is present, `Forwarded: for=`) from right to left, skips the
listed hops, and takes the first address that is not listed. First-run setup's throttle works the same way. The audit log is unchanged: it still
records the first forwarded address, with `peerIpAddress` next to it when that differs.

**Upgrade:** if ShadouCMDB runs behind a reverse proxy or load balancer, set `TRUSTED_PROXIES` to its
address as the server sees it, or to the CIDR range of a proxy pool (for example
`TRUSTED_PROXIES=10.0.0.5` or `TRUSTED_PROXIES=10.20.0.0/24,fd00:1::/64`). Without it, every client
counts as the proxy's network, so one client's wrong passwords lock a username for everyone behind
that proxy. List only proxies you run; `0.0.0.0/0` and `::/0` are refused at start-up. The server logs
a warning at start-up while the list is empty. No API or schema change.
