### Added: Moving workflow instances to a newer version, bulk transitions, and a workflow archive

- **Instance migration.** `POST /api/v1/admin/workflow-definitions/{id}/instance-migrations` with
  `fromVersionNo`, `toVersionNo`, `stateMap` and `dryRun` moves the running instances of one version
  to a newer published version. `stateMap` maps each old state key to a new one. A state you leave
  out moves to the state of the same key in the new version, if there is one. A state that still has
  running instances and nowhere to go is refused with `400 VALIDATION_ERROR` (`unmapped`), in a dry
  run too. Run with `dryRun: true` first: it reports how many instances each state holds and where
  they would go, and writes nothing. This needs **Manage workflows** and the view and edit rights on
  every type the workflow runs on. A real run moves up to 1,000 instances per transaction. If it is
  interrupted, the moved batches stay moved; run it again to move the rest. Each moved instance is
  recorded on its CI as `workflow.migrate`, and as a `migrate` event in its history. When the new
  state maps to a different value of the workflow's state field, the CI's field is updated as well.
- **Bulk transitions.** `POST /api/v1/workflow-instances/bulk-transitions` runs up to 500 transitions
  in one request. Each item is checked exactly like a single transition, with the same rights, grants
  and audit rows. An item that is refused is rolled back on its own and reported with the error the
  single endpoint would return. The other items are committed together. The response always has one
  result per item, in the order of the request.
- **Workflow archive.** When a type is purged, the workflow instances of its CIs now move to an
  archive with their full history, in the same transaction. Before, such a purge failed. The archive
  is never changed or deleted, and audit log retention (`shadoucmdb prune-audit`) does not touch it.
  `GET /api/v1/admin/workflow-archive` lists it (**Manage workflows**, for users whose profile does
  not limit the types they may view). Each entry's `requestId` matches the CI's `delete` audit entry.

**Upgrade:** migration 0050 adds the `workflow_instance_archive` table and a trigger that archives a
CI's workflow history when the CI row is deleted. No existing row changes. On a three-role install,
the API role may only read the archive. The trigger writes it with the schema owner's rights.
