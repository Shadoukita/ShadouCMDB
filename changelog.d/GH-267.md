### Security: making a field required, a type abstract, or moving a type needs view on the CIs it checks

Since [GH#221] a field change checked against stored values needs the view right on the field's type and every
type below it. Three data-model changes were still checked against stored CIs without it ([GH#267]), so whether
they succeeded told a user with the data-model permission something about CIs of types they may not view, and the
preview (`POST /api/v1/schema-changes/preview`) answered without leaving an audit entry:

- `isRequired: true` on a field, or a new required field: whether any CI of the type lacks a value, or whether
  the type has any CI at all;
- `isAbstract: true` on a type: whether the type holds any CI;
- a new `parentId`: whether the moved CIs hold values the new parent does not provide, or lack its required ones.

These changes now answer `403 FORBIDDEN` (`details[].code` `view_required`) before any CI is read unless the user
may view every type checked (the type and every type below it; for `isAbstract`, the type itself). A refused
preview is audited as `schema_change.refused`. Types created in the same transaction, as in a configuration
import, hold no CIs yet and are not checked. Users who may view the types see the same answers as before; the
`isRequired` refusal now always states how many CIs lack a value, and the re-parenting refusal always names the
fields, since only such users reach them.
