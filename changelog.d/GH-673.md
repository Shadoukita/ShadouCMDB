### Security: the first start of a replacement workflow needs the `_start` grant where the old one ran

After a holder of `workflows.manage` replaced the workflow that drives a state field (deactivated
workflow A, then activated workflow B on the same field), any user with the edit right on the CI's
type could start B on a CI where A had already run. The new instance set the state field back to
B's initial state, undoing a lifecycle that may have passed approval ([GH#673]).

- `POST /api/v1/workflow-instances` now needs `workflows.manage` or the workflow's `_start` grant
  when an instance of the same workflow ended on the CI (as before, [GH#666]) **or** when any
  instance of another workflow on the same state field exists on the CI, whether it is running,
  completed or cancelled. Otherwise it returns `403 FORBIDDEN`. On a CI where no workflow on that
  field has run, the first start still needs only the edit right.
- `GET /api/v1/configuration-items/{id}/workflows` applies the same rule to `startable`.

**Upgrade:** no migration. If you replace a field's driving workflow and other teams start it on
existing CIs, grant `_start` on the new workflow to their profiles.
