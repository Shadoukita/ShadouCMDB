### Security: a backup.restore entry `restore` did not send reaches the SIEM anyway

Since the previous release `shadoucmdb restore` sends its `backup.restore` entry to `AUDIT_EXPORT`
itself, so that someone with the API role's credentials cannot hide it by marking it as sent before
the server starts. When `restore` did not send it (an `AUDIT_EXPORT` of `stdout`, an export file that
did not exist yet, or a failed send), the entry still depended on that list, and such a person could
keep it from the SIEM copy. ([GH#716])

- `restore` now records its entry in `audit_export_restore_pending`, in the restore's own
  transaction, and removes it only once its own send succeeded. The API role may read that table
  but not change it.
- The server's audit export sends every entry still recorded there each time it starts, whatever
  `audit_export_restores` lists as sent, and logs a warning for each. The collector may therefore
  receive the entry more than once, with the same `chainSeq` and `rowHash`.
- `restore` now prints a warning when it did not send the entry, naming the `chainSeq` to look for
  in the collector.

**Upgrade:** migration `0066` adds the table `audit_export_restore_pending` (included in backups) and
grants the API role `SELECT` on it. To apply it, run `shadoucmdb migrate` before starting the new
release. Restores done before the upgrade are unaffected: their entries are handled as before.
