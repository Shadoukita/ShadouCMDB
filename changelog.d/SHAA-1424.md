### Added: Running workflows on CIs (runtime API)

Published workflows can now run on CIs through `/api/v1/workflow-instances`. API tokens may use
these endpoints.

- **Start.** `POST /api/v1/workflow-instances` with `definitionKey` (or `definitionId`) and `ciId`
  starts an active, published workflow on a CI of its type. This needs the edit right on the type. A
  CI runs at most one instance of each workflow. The instance stays on the version it started on.
- **Transitions.** `POST …/{id}/transitions` with `transitionKey`, `expectedVersion`, the
  transition's `fields` and a `comment`. The fields are validated as a CI edit validates them. Missing
  required fields, a missing required comment and failing conditions return
  `422 WORKFLOW_CONDITION_FAILED`, with one detail for each (`fields.<key>` or `comment`). Running a
  transition needs the edit right on the CI's type and a grant of the transition to one of your
  permission profiles. **With an API token, the token's profile must be granted the transition as
  well**, so a narrowly scoped token cannot approve a step its owner could. The Administrator profile
  may run every transition.
- **State field.** When a workflow has a state field, starting, transitions and forced states write
  it on the CI. That write appears in the CI's history as a normal edit.
- **Cancel and force.** `POST …/{id}/cancel` (needs **Manage workflows**, or the `_cancel` grant with
  the edit right) and `POST …/{id}/force` (needs **Manage workflows** and the edit right) both take a
  mandatory reason. Deleting a CI cancels its running instances in the same transaction.
- **Reading.** `GET …/{id}` returns the instance, the graph of its version and the transitions you may
  run, each with its fields and the conditions that currently block it (`blockedBy`).
  `GET …/{id}/events` lists the instance's history. `GET /api/v1/workflow-instances` is a paged,
  filterable list and `GET …/summary` counts running instances per state.
  `GET /api/v1/configuration-items/{id}/workflows` returns a CI's running and recent instances and the
  workflows you may start on it.
- **Visibility.** An instance on a CI of a type you may not view does not exist for you: 404 on every
  endpoint. It is also left out of lists and counts.
- **Audit.** Starts, transitions, cancellations and forced states are recorded on the CI
  (`workflow.start`, `workflow.transition`, `workflow.cancel`, `workflow.force`), so they appear in the
  CI's history and follow its visibility rules. Instance events are kept for the life of the CI;
  audit log retention does not remove them.

Not yet in this release: refusing direct edits of a workflow-driven state field, starting instances
on existing CIs in bulk (`bootstrap`) and automatic start on CI creation. They follow in SHAA-1424's
follow-up slice.

Operators: `tools/perf/workflows.sh` measures the runtime on 500 000 CIs.
