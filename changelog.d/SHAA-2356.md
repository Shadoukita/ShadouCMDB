### Added: in-app notifications

Each user now has an inbox of notifications for the bell in the web UI:

- **Approval waiting** (`approval_requested`): a step of an approval request became active and you
  may decide it. The requester is never notified about their own request.
- **Approval closed** (`approval_closed`): your approval request was approved, rejected, or closed
  by someone else (a manager's cancel, the instance cancelled or forced, the CI deleted, a
  migration). Withdrawing your own request does not notify you.
- **Workflow transition** (`workflow_transition`): someone else ran a transition on, cancelled or
  forced a workflow instance you started. A transition that ran because your own approval request
  was approved is reported as the approval outcome only.
- **Import finished** (`import_finished`): your import completed, completed with errors, or failed.

Notifications are written in the same database transaction as the event, so an action that is
rolled back notifies no one. A user sees only their own notifications, administrators included.
A notification about a CI is listed only while the user may view the CI's class. Deactivated
accounts receive no new notifications, and a user's notifications are deleted with the account.

New endpoints, for signed-in sessions only (API tokens get 403): `GET /api/v1/notifications`
(paginated, filters `unread` and `kind`), `GET /api/v1/notifications/unread-count`,
`PATCH /api/v1/notifications/{id}` (`read: true|false`), `POST /api/v1/notifications/mark-read`
(optionally `upTo`, so notifications that arrived since stay unread) and
`DELETE /api/v1/notifications/{id}`. Marking read and dismissing change only the user's own inbox
and are not recorded in the audit log. Nothing is sent outside the application: no e-mail, webhook
or push.

Notifications are kept for `NOTIFICATION_RETENTION_DAYS` days (default 90), and at most the newest
500 per user. Each server process deletes older ones once an hour.

**Upgrade:** migration `0072` adds the `notifications` table and its triggers on approval
requests, workflow instance events and import jobs. Existing data is not back-filled. Backups
include the table. Run `shadoucmdb migrate` before starting the new release.
