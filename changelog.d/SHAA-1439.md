### Security: Audit chain tampering by the schema owner or a backup editor is detected

Three gaps in the tamper detection of the audit hash chain are closed. Each needed the schema owner's
rights or write access to a backup file; the API role could not exploit them, and the SIEM copy
(`AUDIT_EXPORT`) remained the authority throughout.

- `shadoucmdb audit-verify` now checks the chain head. Rewriting the newest audit rows and recomputing
  their hashes used to leave a chain that verified; `audit_log_chain_head` keeps the hash the insert
  trigger wrote, and a mismatch is reported as a `head` finding. The head printed by `audit-verify` is
  now the one `audit_log_chain_head` records, which is the value to compare with the SIEM copy. ([GH#511])
- `audit-verify --allow-gaps` accepts only gaps a `prune-audit` run accounts for: the missing rows are
  older than the cutoff of a later `audit.purge` entry, and that cutoff respects the 30-day floor. Such
  a gap is reported as `retention`; any other gap is `deleted` and fails even with `--allow-gaps`.
  ([GH#512])
- `shadoucmdb backup` seals the end marker of the file with an HMAC-SHA256 under a key derived from
  `ENCRYPTION_KEY_FILE`, so a file edited after the backup, with its SHA-256 recomputed, is refused by
  `restore`. `restore` checks the seal with `ENCRYPTION_KEY_FILE` or `ENCRYPTION_KEY_PREVIOUS_FILE` and
  records a `backup.restore` audit entry (`entityType` audit_log) naming the backup, how its seal
  checked out (`verified`, `unsigned` or `unknown_key`) and the chain head it restored; the server's
  `AUDIT_EXPORT` sends it at start-up, so a rolled-back chain shows in the SIEM copy. ([GH#513])

Backups keep their format version: older ShadouCMDB releases still read new backups and ignore the
seal. A backup without a seal (written before this release, or by `backup` without
`ENCRYPTION_KEY_FILE`), or sealed with a key that is not configured, is restored only with the new
option `restore --allow-unsigned`, after you have checked where the file came from.

**Upgrade:** migration `0053` replaces `audit_log_verify()` and allows the `backup.restore` audit
action; to apply it, run `shadoucmdb migrate` before starting the new release (`serve` does not
migrate). Run `backup` with the server's `ENCRYPTION_KEY_FILE` so new backups are sealed. To restore
a backup taken before this release, add `--allow-unsigned`. Scripts that run
`audit-verify --allow-gaps` fail on a gap no `prune-audit` run accounts for: investigate it against
the SIEM copy.
