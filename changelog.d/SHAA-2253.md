### Security: `shadoucmdb restore` sends its backup.restore entry to the SIEM itself

After a restore, the server's audit export sends the `backup.restore` entry when it starts and then
lists the entry in `audit_export_restores`, so a restart does not send it again. The API role could
insert into that table itself. With the API role's credentials (for example through SQL injection or
stolen application credentials) an attacker could list the real entry between `shadoucmdb restore`
and the first start of the server. The export then started past the entry, and the SIEM copy never
learned of the rollback. ([GH#706])

- `shadoucmdb restore` now sends its `backup.restore` entry to the configured `AUDIT_EXPORT` sink
  as soon as the restore is committed, and reports whether it did. It does not send to `stdout`
  (during a restore that is the operator's terminal) or to an `AUDIT_EXPORT` file that does not
  exist yet (the restore would create it with the wrong owner). If the send fails, `restore` prints
  a warning: until the collector shows the entry's `chainSeq`, tell whoever reviews the SIEM about
  the restore.
- The server's export still sends the entry when it starts, with every row written after it. The
  collector therefore receives the entry twice, with the same `chainSeq`, `id` and `rowHash`.
  Deduplicate on `chainSeq` if your SIEM counts events.
- The API role no longer has `INSERT` on `audit_export_restores`. It lists an entry only through
  `cmdb.audit_export_mark_restore_sent()`, which accepts one existing `backup.restore` entry at a
  time and records the time of the call. The maintenance role cannot execute it.

The database cannot tell the server's export apart from someone else who holds the API role's
credentials. Such a person can still call the function and stop the server from sending the entry
again. They cannot stop the copy that `restore` sends itself.

**Upgrade:** migration `0064` adds the function and changes the API role's grants on
`audit_export_restores` to `SELECT`. Entries already listed stay listed. To apply it, run
`shadoucmdb migrate` before starting the new release (`serve` does not migrate). On a single-role
install, where the API connects as the schema owner, the grants are unchanged.

**Upgrade, single-role installs that split later:** `sql/bootstrap/10_split_roles.sql` granted the
API role `INSERT`, `UPDATE` and `DELETE` on every `cmdb` table, `audit_export_restores` included,
and handed the function to the owner role without `EXECUTE` for the API role. It now leaves the
API role `SELECT` on the table and grants it `EXECUTE` on the function. If you ran the split script
after migration `0064` was applied, run it again (it is safe to re-run), as described in its
header. Otherwise the export cannot list entries and sends each `backup.restore` entry again on
every start.

`shadoucmdb restore` appends to an existing `AUDIT_EXPORT` file only if the path is not a symlink.
