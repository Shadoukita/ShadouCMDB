### Security: The API role can no longer mark a future backup.restore entry as sent

The audit export lists each `backup.restore` entry it has sent in `audit_export_restores`, and the
API role could add any chain sequence number there. With the API role's credentials (for example
through SQL injection or stolen application credentials) an attacker could list numbers past the
current end of the audit log. The entry a later `shadoucmdb restore` wrote at one of those numbers
then counted as sent, the export started past it, and the SIEM copy never learned of the rollback.
([GH#696])

`audit_export_restores` now accepts only the chain sequence number of an existing `backup.restore`
entry; any other value is refused with a foreign key violation, for every database role. `sent_at` is
set to the time of the insert. `shadoucmdb restore` removes rows that match no restored
`backup.restore` entry before it records its own entry, so a backup taken while such rows existed
cannot hide the restore either.

**Upgrade:** migration `0063` adds the check as a trigger on `audit_export_restores` and removes rows
that match no `backup.restore` entry in the audit log. It runs on start as usual. If the migration
removed rows, they did not come from the audit export, which only lists entries it sent: review who
had the API role's credentials. Restoring a backup taken before the upgrade applies the same cleanup.

[GH#696]: https://github.com/Shadoukita/ShadouCMDB/issues/696
