### Security: refused uses of a dead API token are no longer lost from the audit log

Refused requests with a token that can no longer authenticate (revoked, expired, owner disabled, MFA
requirement unmet, profile deleted) are recorded at most once a minute per token and outcome. The uses
left out were counted in memory and written only on the next recorded row. So when a replay stopped
within the minute, or the server restarted, those uses appeared nowhere. A revoked token replayed 1,000
times in 50 seconds left a single audit row, which made it hard to judge how heavily a leaked token was
used ([GH#213]).

The server now writes a summary `token.use` row for each window that left uses out, about 10 seconds
after the window ends and for every open window at graceful shutdown. The row has `outcome`,
`unrecordedRefusals`, `windowStart` and `windowEnd`, no request path or client address, and the actor
`system` / `API token refusal summary`. The first refused use in each window is recorded as before, so
existing SIEM rules on `token.use` keep working. A server that is killed rather than stopped still loses
the counts of its open windows.

No configuration change. Sum `unrecordedRefusals` over a token's `token.use` rows to get the number of
refused uses the audit log did not record one by one.
