### Security: request bodies are no longer read before the caller is authenticated

The API read the whole request body into memory before it checked who was calling. Configuration
import accepts 16 MiB, so a few hundred anonymous, slowly sent import requests could make the server
hold gigabytes of memory until `HTTP_REQUEST_TIMEOUT_SECS` expired, only to answer each with
`401 UNAUTHENTICATED` ([GH#181]). The server now checks the session or API token, the CSRF token and
the permission first, and reads the body only afterwards, streaming it and stopping as soon as it
passes the route's limit. A declared `Content-Length` above the limit is refused without reading.
The public routes (first-run setup and sign-in) now accept at most 64 KiB.

The new `HTTP_MAX_CONCURRENT_REQUESTS` setting (default 512) caps the requests handled at once.
Further requests are answered `503 SERVER_BUSY` with `Retry-After: 1` instead of queueing; `/healthz`
is exempt.

**Upgrade:** nothing to do. If a monitored instance legitimately handles more than 512 requests at
once, raise `HTTP_MAX_CONCURRENT_REQUESTS`. API clients should retry `503 SERVER_BUSY` after the
`Retry-After` delay.
