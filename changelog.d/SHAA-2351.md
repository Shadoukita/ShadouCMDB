### Added: Data-quality checks for the dashboard ("Needs attention")

`GET /api/v1/configuration-items/data-quality` returns four checks with the number of CIs each
finds, among the active, live CIs in classes the caller may view (process records left out, as in
the inventory list):

- `no_owner`: no value in the owner field of the CI's class (a blank text counts as no value).
- `end_of_life`: end of life today or earlier, or within `endOfLifeWithinDays` days (default 90,
  0 to 3650), by the database server's date.
- `no_relationships`: no live relationship, in either direction, to a CI the caller may view.
- `pending_approval`: a workflow approval request on the CI is pending.

Each check carries a `filter` with the query parameters that list its CIs. The inventory list
(`GET /api/v1/configuration-items`) and its facet counts accept the same parameters, `quality` and
`endOfLifeWithinDays`, and can be combined with every other list filter.

Classes have two new settings, `ownerAttributeId` and `endOfLifeAttributeId`, which name the field
of the class (or an inherited one) that holds a CI's owner (text, enum, lookup or reference) and
its end of life (date or datetime). A class without its own setting takes its parent's, so one
setting on a root class covers its subclasses, and a subclass can name a different field. CIs of
classes with no setting in their lineage are not counted by those two checks; when no class the
caller may view has a setting, the check reports `configured: false` so the dashboard does not
show a reassuring 0. Changes to the settings are recorded in the audit log like any other class
change. A field named by a setting cannot be changed to a type the setting does not accept, and
deleting the field clears the setting. Configuration files now carry both settings
(`ownerAttribute`, `endOfLifeAttribute`; format version 11). When you import an older file,
existing classes keep their settings.

The endpoint is read-only and writes nothing to the audit log.

**Upgrade:** migration `0068` adds `owner_attribute_id` and `end_of_life_attribute_id` to
`ci_classes`. It sets them on classes that define a field with a conventional key: `owner` (text,
enum, lookup or reference) for the owner field, and `end_of_life`, `end_of_life_date`, `eol` or
`eol_date` (date or datetime) for the end-of-life field. Each class it changes gets an audit entry
by "migration 0068". Review the settings of your classes afterwards, and set them where your
fields use other keys. Run `shadoucmdb migrate` before starting the new release.
