### Security: a split single-role install gives the API role the same rights as a fresh install

`sql/bootstrap/10_split_roles.sql` converts an install made with the older single-role setup to the
three roles. It granted the API role `SELECT`, `INSERT`, `UPDATE` and `DELETE` on every `cmdb` table
and then repeated only some of the restrictions the migrations make on a fresh install. On a split
install the API role therefore kept `INSERT` on the workflow archive (`workflow_instance_archive`),
which on a fresh install only the database trigger writes when a CI is deleted, and `UPDATE` and
`DELETE` on workflow history (`workflow_instance_events`), approval decisions
(`workflow_approval_decisions`) and the archive. With the API role's credentials (for example through
SQL injection or stolen application credentials) an attacker could add invented workflow history for
deleted CIs to the archive. Changing or deleting history and decisions stayed blocked by the
append-only triggers, which the API role cannot switch off; the grants were the missing second
line. ([GH#713])

- The API role's rights on system tables and routines are now listed in one place,
  `cmdb.api_role_privileges`, and applied by `cmdb.apply_api_role_grants()`. Migrations and the split
  script both use it, so a later restriction applies to split installs too.
- The split script now needs migration `0065` and stops with a message if it is not applied: run
  `shadoucmdb migrate` of the new release first, as its header already says, and use the script that
  comes with that release.
- The API role no longer gets default rights on tables created later in schema `public`, which holds
  only `_sqlx_migrations` and extensions. It keeps `SELECT` on `_sqlx_migrations`.

To compare the API role's rights with a fresh install's, run
`psql "<admin connection string>" -XAt -f sql/checks/api_role_privileges.sql` on both databases.

**Upgrade:** migration `0065` applies the list on every three-role install, which repairs an install
split with an earlier release. No data changes, and nothing else is needed. On a single-role install,
where the API connects as the schema owner, the grants are unchanged until you split the roles.
