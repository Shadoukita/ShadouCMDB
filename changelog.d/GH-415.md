### Security: a failed sign-in no longer writes an unknown username to the server log

The `sign-in failed` warning logged the username as typed, even when it matched no account
([GH#415]). A name that matches no account is often a password typed into the username field, and
the server log (stdout, journald, a log shipper) is usually readable by more people than the audit
log. The warning now names the account only when the username matches an existing local or
directory-linked account; otherwise it carries `unknown_user=true` instead of the name. It also
carries `request_id`, the request id of the `login.failure` audit row for the same attempt.

The `login.failure` and `login.locked` audit rows are unchanged: they keep the name as typed in
`attemptedUsername`, for real and unknown names alike, so that the audit log does not reveal which
names exist and brute-force attempts can still be investigated. Reading them requires the audit
permission, and the audit retention period removes them.

**Upgrade:** nothing to do. Log searches and SIEM rules that read `username` from `sign-in failed`
lines should also handle `unknown_user=true`; to see the name typed in such an attempt, look up the
audit row with the line's `request_id`.

[GH#415]: https://github.com/Shadoukita/ShadouCMDB/issues/415
