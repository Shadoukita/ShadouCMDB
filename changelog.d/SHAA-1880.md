### Added: Approval requests on workflow transitions (run time)

- Running a transition that has an approval policy now creates an approval request instead of
  moving the instance. The request is checked like any transition: the grant, the edit right,
  the fields sent, the required fields, the comment and the conditions. Nothing is written to the
  CI. The fields and the comment are staged in the request, and `POST
  /api/v1/workflow-instances/{id}/transitions` answers **202** with the instance, still in its
  state, and its new `pendingApproval`. This replaces the 409 `CONFLICT` (`approval_required`) of
  the previous release.
- While a request is pending, the instance runs no other transition. Such a transition is refused
  with **409 `WORKFLOW_APPROVAL_PENDING`**. `availableTransitions` marks each transition as blocked
  (`approval_pending`), and also says which transitions need approval (`requiresApproval`,
  `approvalSteps`).
- New endpoints under `/api/v1/workflow-approval-requests/{id}`: `GET` (steps, decisions,
  requester and your eligibility), `POST …/decisions`, `POST …/withdraw` (the requester only) and
  `POST …/cancel` (holders of `workflows.manage`, or of the `_cancel` grant with the edit right; a
  comment is required). Every endpoint answers 404 for a CI the caller may not view.
- **Deciding** needs the view right on the CI's type and a place among the active step's approvers.
  It needs no edit right. Steps run in order, and each needs its quorum. Any rejection rejects the
  request (a comment is required), and the instance stays where it is and can request again. The
  final approval applies the transition in the same transaction. Only the staged fields that the
  transition takes are written, together with the state field, through the normal item validation.
  The decider is the actor, with the edit right on the CI's type and no view right beyond their
  own. If a staged field changed since the request, the conditions no longer hold, or the request
  stages a field the transition does not take, the final approval is refused with **409
  `WORKFLOW_APPROVAL_STALE`**. Nothing is recorded, not even the decision.
- **Four-eyes** is always on and keyed by user account. These decisions are refused with **403
  `WORKFLOW_APPROVAL_SELF`**:
  - the requester, through any profile, session or API token (`requester`);
  - a token the requester minted for someone else (`token_creator`);
  - with `distinctFromEarlier`, whoever approved an earlier step (`earlier_step`);
  - with `excludeActorsOf`, whoever requested, applied or approved those transitions on the
    instance (`actor_of:<key>`).
- **API tokens** decide only on steps with `allowApiTokens`, and only through a token its owner
  minted for themselves. Otherwise the decision gets 403 `FORBIDDEN`, with reason
  `session_required` or `token_not_self_minted`. Requests and decisions record the token and its
  creator.
- The request's `requester` shows live whether the account is still active and still holds the
  right to make the change (`stillAuthorized`). This is advisory: it does not block a decision.
- **Closing a request:**
  - Cancelling or forcing an instance closes its pending request (`instance_cancelled`,
    `instance_forced`). The `workflow.force` audit row names the overridden request.
  - Deleting the CI closes it (`ci_deleted`).
  - Instance migration takes `pendingApprovals: "skip" | "cancel"` (default `skip`): `skip` leaves
    such instances on their version, and `cancel` closes their requests (`instance_migrated`).
    The report counts `pendingApprovals` and `skipped`.
  - In a bulk transition, a gated item reports the request it created (`approvalRequestId`).
- Audit: `workflow.approval_request`, `workflow.approval_decide` and `workflow.approval_close` rows
  on the CI. The CI `update` row and the `workflow.transition` row of a final approval both carry
  `approvalRequestId` and `requestedBy`. Instance events gain the `approval_*` kinds with
  `approvalRequestId` and `approvalStepNo`.
- Not yet in this release: delegation, and overdue handling and escalation.
