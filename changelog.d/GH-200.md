### Security: API tokens follow their owner's two-factor requirement

API tokens now follow the two-factor requirement of their owner. When a permission profile the
owner holds requires two-factor authentication (and, for OIDC accounts, the provider is not trusted
to enforce it), a token is accepted only if it was created from a session signed in with a second
factor. Earlier tokens without one are refused with 401 and a `token.use` audit event with outcome
`mfa_required`; create new tokens for them. `shadoucmdb migrate` reports how many tokens this
affects. Accounts without such a profile, such as dedicated automation accounts, are not affected
([GH#200]).

- The token list and item show `mfaVerified` and `refusedForMfa`;
  `GET /api/v1/admin/api-tokens?refusedForMfa=true` lists the refused tokens.
- Creating a token that would be refused answers `403 MFA_REQUIRED_FOR_TOKEN`. For an automation
  account under `requireMfa`, an administrator signed in with a second factor creates the token.
- The rule is checked on every request: when the requirement is removed, refused tokens work again.

**Upgrade:** check before upgrading, and **stop the server before `shadoucmdb migrate`**. Migration
0024 renames `sessions.provider_mfa` to `sessions.mfa_verified` and adds `api_tokens.mfa_verified`.
The previous version reads the old column at every sign-in and signed-in request, so it fails if it
keeps running after the migration, and it cannot run against the migrated database. Take a backup
first: to roll back, restore it and start the previous version. Existing tokens count as created with a
second factor when their creator had a confirmed authenticator at the time; all others do not.
`shadoucmdb migrate` and `shadoucmdb verify` print how many working tokens of how many accounts are
refused. List them with `GET /api/v1/admin/api-tokens?refusedForMfa=true` and create new tokens for
the affected integrations.
