### Security: Inventory CSV exports can no longer take the database connections the rest of the API needs

Each inventory CSV export (`GET /api/v1/configuration-items/export`) holds a database connection
while the client downloads the file. The number running at once was fixed at 4, whatever
`DATABASE_POOL_MAX` was, and a client that read slowly kept its connection for up to 30 minutes.
With a small pool, two signed-in users could make the API answer `503 DATABASE_UNAVAILABLE` to
everyone, sign-in included ([GH#801]). Now:

- The number of exports running at once is `EXPORT_MAX_CONCURRENT`, by default an eighth of
  `DATABASE_POOL_MAX` (at least 1; 1 with the default pool of 10). A value you set must leave at
  least 2 connections free when impact analyses (`IMPACT_MAX_CONCURRENT`) and saved-view counts (a
  quarter of the pool) use theirs too; otherwise the server does not start and says which
  settings to change. More exports are answered `503 SERVER_BUSY`; a user still runs at most 2.
- A download is cut off when the client stops reading for 15 seconds (was 30), when it reads
  slower than 32 KiB/s once it has kept the server waiting 30 seconds in all, or after 10 minutes
  in total (was 30). As before, a download cut short ends with a broken connection, never with a
  file that looks complete.
- Starting an export no longer waits for a second connection while it holds one; exports start
  one at a time.

**Upgrade:** with the default pool of 10, one export runs at a time instead of four. If your users
export often or concurrently, raise `DATABASE_POOL_MAX` (an eighth of it, rounded down, is the
default) or set `EXPORT_MAX_CONCURRENT` within the limit above. Very large exports over slow links
may now need a filter to finish within 10 minutes.
