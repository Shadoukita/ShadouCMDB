### Added: Database schema for approvals on workflow transitions

- This release adds the tables that later releases use for approvals on workflow transitions:
  approval steps on a transition, approver assignments, time-boxed delegations, approval requests
  with their steps, the approvers resolved for a step, and the approve and reject decisions. No API
  reads or writes them yet, and nothing changes for an install until a workflow version with an
  approval step is published.
- The database enforces the rules that approvals will depend on. A published version's approval
  steps cannot be changed. An instance has at most one pending request. Each person has one vote
  per step, whether they vote themselves or on behalf of someone. A delegation lasts at most 90 days
  and cannot name the same user on both sides. Decisions can never be updated or deleted. On a
  three-role install, the API role may only read and add them.
- Deleting a user keeps every delegation the user was part of, with the user's name. Approval
  decisions made through a delegation are kept unchanged.
- When a type is purged, the workflow archive now also keeps the approval requests of each instance,
  with their steps and decisions (`approvals`). Archive entries written before this release have no
  `approvals`.
- The audit log accepts four new actions, `workflow.approval_request`, `workflow.approval_decide`,
  `workflow.approval_close` and `workflow.approval_overdue`, and the entity type
  `workflow_approval_delegations`. The audit log page offers them as filters. Retention
  (`shadoucmdb prune-audit`) treats them as part of the `changes` scope.

**Upgrade:** migrations 0051 and 0052. Migration 0051 creates the new tables. It also adds three
nullable columns to `workflow_instance_events` and an `approvals` column to
`workflow_instance_archive`. No existing row is rewritten. It re-adds the event kind and audit
action CHECK constraints `NOT VALID`. Migration 0052 then validates them in a transaction of its own
and takes only a `SHARE UPDATE EXCLUSIVE` lock, so the API can keep writing events and audit entries
while 0052 scans the tables. Back up before upgrading, as for every release. `shadoucmdb backup`,
restore and factory reset include the new tables without any configuration.
