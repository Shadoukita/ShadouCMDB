### Security: a generated setup token written to the token file is no longer logged

While no user exists, the server generates a one-time setup token; whoever holds it creates the
first administrator. The token was written to the token file (`SETUP_TOKEN_FILE`, readable only by
the service account) **and** logged in clear in a `WARN` line ([GH#436]). Everyone who can read the
log (the `adm` and `systemd-journal` groups, log shippers and SIEMs, `docker logs`, or a
`--log-file` created with a permissive umask) could take over a new installation.

- When the token file was written, the log line names only the file (`file=...`), never the token.
- The token is logged (`setup_token=...`) only when there is no token file or it cannot be written,
  as before.

The Linux and Windows instructions now read the token from the file. A container has no token file
by default, so its token is still in the container log: where too many people can read that log,
create the first administrator with `create-admin` or set `SETUP_TOKEN` (see the README).

**Upgrade:** nothing to do; no schema or configuration change. A token already logged by an earlier
version stops working once the first administrator exists.
