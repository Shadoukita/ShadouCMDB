### Security: workflow administration follows the manager's type permissions

The `workflows.manage` permission let a manager whose profile is limited to some CI types read and
change workflows on any type ([GH#667]): their settings (including `isActive` and `autoStart`),
drafts, versions, grants and approvers, through the admin API and the configuration import.
Bootstrap and instance migrations already required the rights on every type a workflow covers; the
other routes under `/api/v1/admin/workflow-definitions` now do too:

- **Reading** a workflow (the definition, its versions, draft, validation, grants, approvers and
  approver preview) needs the view right on every type it covers: its type, and the types below it
  when it includes subtypes. Otherwise the workflow answers `404 NOT_FOUND`, as a missing one does,
  and the list leaves it out.
- **Changing** it (settings, delete, draft, publish, retire, grants, approvers) needs the view and
  edit rights on all those types; with view only, the request is refused with `403 FORBIDDEN`.
  Creating a workflow needs them on the chosen type (and its subtypes with `includeSubclasses`).
- The **configuration export** leaves out the workflows the caller may not read, and the
  **import** skips, with a warning, each workflow on types the caller may not both view and edit.

Administrators and profiles with rights on all types are not affected. No API schema or database
change.

**Upgrade:** check the profiles that hold `workflows.manage`. A profile with that permission but no
view right on a workflow's types no longer sees the workflow; give it the type rights it needs.
